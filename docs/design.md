# LinkForge 关键设计决策

这份文档记录**为什么这么做**，而不是做了什么（做了什么看代码和 README）。
每条都写清楚：选了什么、放弃了什么、什么情况下该改主意。

---

## 一、短码怎么生成：号段模式 + Base62

### 选了什么

数据库维护一张 `t_id_segment` 表，每个业务一行。应用取号时执行
`UPDATE t_id_segment SET max_id = max_id + step WHERE biz_tag = ?`，
把 `[max_id+1, max_id+step]` 这一整段独占下来，在内存里用 `AtomicLong` 分发，
用完了再取下一段。拿到的 id 用 Base62 编码成短码。

### 放弃了什么

| 方案 | 优势 | 为什么没选 |
|---|---|---|
| 数据库自增 | 最简单 | 每插一行访问一次 DB，高并发下自增锁直接成瓶颈；而且自增 id 暴露业务量 |
| 雪花算法 | 完全不依赖 DB，性能最好 | 依赖机器时钟，时钟回拨会发出重复 id，得额外做回拨检测；workerId 的分配也是个运维问题 |
| Hash 取模 | 短码长度可控 | 有碰撞，要存碰撞记录并重试；还要处理"同一个长链接要不要复用短码"的歧义 |

### 代价

**重启会浪费一段没用完的号。** 服务在号段还剩 300 个时重启，那 300 个 id 就永远
没人用了。短链场景 id 量级不大，这个浪费可以接受 —— 换 Snowflake 就得接受时钟回拨风险，
两者选一个更可控的。

另外，**号段模式发出的 id 是递增的**，理论上可以被遍历。
如果短链需要"不可猜测"，得在 Base62 之后再加一层混淆（比如把 id 按位异或一个常量再编码），
本项目没做 —— 因为短码的用途是"短"而不是"保密"，真正的访问控制靠的是短链的启停和过期。

### 实现上的一个坑（已修）

取号段时，**号段上限的快照必须早于游标递增**：

```java
// 对的
long segmentMax = buffer.maxIdInSegment;
long current = buffer.cursor.getAndIncrement();
if (current <= segmentMax) { return current; }
```

反过来的话，本线程可能拿的是**旧号段**的游标值，却读到别的线程刚换好的**新上限**，
于是"旧值 <= 新上限"成立、这个 id 被提前发出去；而新号段的游标稍后推进到
同一个数值时还会再发一次 —— **重复 id**。

这个窗口只有几条指令宽，实测在 32 线程 / 16 核下跑 200 轮一次都没复现；
只有在两次读之间插入人为停顿（模拟被 OS 抢占或 GC 停顿）时才稳定复现（200 轮里 33 轮出现）。
换句话说：**它是真的，但极其罕见**。修它的成本是两行，不修的风险是数据覆盖。

## 二、跳转链路的四层防护

跳转 `GET /{shortCode}` 是整个系统里唯一的高频路径。四层的作用各不相同：

| 层 | 挡什么 | 做法 |
|---|---|---|
| 布隆过滤器 | **缓存穿透**（查一个根本不存在的短码） | Guava `BloomFilter`，启动时全量加载已有短码 |
| Redis 缓存 | 热点请求 | 普通 key-value，TTL 带随机抖动 |
| 互斥锁 | **缓存击穿**（热点 key 刚好失效） | `SETNX` + TTL，锁内 Double-check |
| 数据库 | 最终一致性 | 兜底 |

### 为什么第一层用布隆而不是"缓存空值"

缓存空值要给每个不存在的短码都存一个 key，攻击者换着花样构造短码能把 Redis 内存撑爆。
布隆用固定大小的 bit 数组：100 万容量 + 1% 假阳性率只占约 1.7 MB，内存不随攻击增长。

代价是**不能删除元素**。所以短链被删除后，短码仍然留在布隆里 ——
这没问题，它只是让请求继续往下走，最终由缓存和数据库判断有效性。

### 为什么 TTL 要加随机抖动

如果所有 key 都写死 30 分钟，一次批量回填或一次重启后的缓存重建会让大批 key
在**同一秒**集体过期，流量瞬间全砸到 DB 上（缓存雪崩）。
每个 key 独立随机 25~35 分钟，过期时刻就摊开了。

### 一个容易漏掉的点：缓存 TTL 不能长过短链寿命

固定 25~35 分钟的 TTL 有个问题：一条**2 分钟后过期**的短链，缓存却按 30 分钟存 ——
过期之后缓存还在，这 28 分钟里它一直在正常跳转，**过期时间形同虚设**。

所以 TTL 取"基础值"和"距离过期还剩多久"的较小值。
实测：75 秒后过期的短链，缓存 TTL 是 74 秒。

### 降级策略

Redis 和布隆过滤器都是 `@Autowired(required = false)` 的可选依赖。
Redis 挂了自动降级成纯 DB 模式，布隆没配上就跳过第一层。

**缓存是性能优化，不该变成可用性的单点。** 降级之后慢，但服务还能用。

但有一条底线：`UserStatusChecker`（账号启用状态）在 Redis 不可用时**退化成每次查库**，
而不是跳过检查 —— "Redis 挂了就跳过状态检查"听起来像优雅降级，
实际上是"缓存一挂，所有被禁用的账号立刻全部复活"。

## 三、为什么跳转链路上一次数据库都不写

每次跳转都 `INSERT` 一条访问明细，高并发下 DB 直接被打满。所以拆成两条路：

```
跳转 → 发事件 → [异步线程池] → Redis INCR（计数）
                              → INSERT t_visit_log（明细）
Redis 计数 → [定时任务，5 分钟] → 批量回写 t_link.visit_count
```

主流程发完事件就返回 302，**一行库都不写**。

### 为什么不直接用 @Async 就完事

Spring Boot 默认给 `@Async` 的线程池是 **core=8、max=Integer.MAX_VALUE、
queue=Integer.MAX_VALUE** —— 队列无界意味着 `max` 永远不生效，实际就是 8 个线程
配一个无界队列。数据库一旦变慢，任务在队列里无限堆积，最后 OOM。

配置成有界队列之后，还必须回答"满了怎么办"。默认的 `AbortPolicy` 会抛异常，
而这个异常是在 `publishEvent()` 提交任务时抛的，会一路冒到 Controller ——
**结果是"日志写不过来"变成了"跳转接口 500"**，一个纯统计功能把核心功能搞挂了。

所以用了自定义的拒绝策略：**丢弃 + 按固定间隔采样记日志**。
丢的是明细（统计数据），而 Redis 里的计数还在，总量不会丢。

### 代价

异步会丢数据：服务崩溃时未消费的事件、队列打满时被丢弃的任务。
**总量准（Redis 计数），明细可能少**。访问统计不是资金数据，这个取舍可以接受。
要更强保证就上 MQ（持久化 + ACK），见"后续可做的事"。

## 四、多租户隔离：让越权"查不到"，而不是"事后检查"

### 做法

所有面向用户的查询**强制带 `user_id`，且 userId 一律从 `CurrentHolder` 取**，
接口签名里根本没有 userId 参数。

```java
// LinkService 的签名里没有 userId —— 想查别人的连入口都没有
PageResult<LinkVO> pageMyLinks(LinkPageQueryDTO dto);
UserProfileVO getProfile();
```

### 为什么不引入 MyBatis-Plus 的租户插件

本项目只有 `t_link` 一张表需要隔离，手写更直观、更可控。表多了再考虑插件。

### 两个具体的坑

**1. OR 条件必须包在括号里。**

```java
.eq(Link::getUserId, userId)          // ← 隔离条件在最外层
.and(w -> w.like(Link::getTitle, kw)  // ← 关键词的 OR 包在 and(...) 里
        .or()
        .like(Link::getShortCode, kw))
```

平铺的话生成的 SQL 是：

```sql
WHERE user_id = ? AND title LIKE ? OR short_code LIKE ?
```

而 AND 优先级高于 OR，实际等价于：

```sql
WHERE (user_id = ? AND title LIKE ?) OR short_code LIKE ?
```

于是"短码匹配上的记录"会绕过 user_id 限制 —— 别人拿一串短码前缀搜索，
就能翻出全站的短链。**这类越权不需要任何攻击技巧，纯粹是括号少写了一个。**

**2. 写操作的归属校验要写进 WHERE 里。**

```java
LambdaUpdateWrapper<Link> wrapper = new LambdaUpdateWrapper<Link>()
        .eq(Link::getId, id)
        .eq(Link::getUserId, userId)   // ← 条件写进 UPDATE 的 WHERE
        ...
```

只靠"先 selectById 查出来判断归属"是不够的：查询和更新之间隔了一段时间，
数据可能变化（TOCTOU）。把条件写进 UPDATE 的 WHERE，隔离才是原子的。

### 管理端是唯一的例外

`/api/admin/**` 下的查询**不带 user_id** —— 管理员本来就要看全部。
它的安全边界从"数据隔离"换成了"角色校验"，由 `JwtTokenInterceptor`
按路径前缀施加。**所以管理端接口的路径必须严格待在 `/api/admin/` 下**，
挪到别的前缀下就只剩登录校验、没有角色校验了。

## 五、JWT 的代价：无状态意味着收不回来

### 选了什么

JWT 无状态：服务端不存任何东西，验签就能确认身份，天然支持横向扩容。

### 代价一：签发出去就作废不了

**"管理员禁用用户"对已经登录的人完全不起作用** —— 他拿着旧 token 照样能调所有接口，
直到 token 过期（本项目 7 天）。这不是理论问题，是实测出来的：
禁用之后重新登录确实被拒了，但旧 token 访问接口仍然返回 200。

修法：拦截器里额外查一次"账号当前是否启用"。为了不让它变成每个请求都查库，
结果缓存在 Redis 里 60 秒；**管理员改状态时会主动删掉缓存，所以禁用是立即生效的**，
60 秒只是"有人绕过接口直接改库"时的兜底刷新周期。

为什么敢在拦截器里加一次 Redis 读：拦截器只作用于 `/api/**`，那是用户管理短链的
低频接口；真正高并发的短码跳转走的是根路径，压根不经过拦截器。

### 代价二：改角色要等 token 过期

角色放在 claims 里（省掉每个请求回查数据库），代价是改了角色要等 token 过期才生效。
把角色当成"登录那一刻的快照"来理解就对了。

### claims 里绝不能放密码

JWT 的 payload 只是 Base64 编码，**不是加密**。任何人复制 token 到 jwt.io 就能看到全部内容。

## 六、AOP 公共字段填充 vs ORM 拦截器

需求明确要求用 AOP 做创建/修改时间和操作人的自动填充。两种方案对比：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **AOP + 反射**（本项目） | 不依赖 ORM；能拿到任意参数 | 依赖"实体是第一个参数"的隐式约定；反射有开销 |
| MyBatis-Plus `MetaObjectHandler` | 更简洁、无隐式约定、无反射开销 | 只对 MP 的 insert/update 生效 |

选 AOP 是因为它不绑定框架。但必须清楚它的软肋：**参数顺序写反了不会报错，
只是字段默默没填上，而且只在数据库里看得出来**。所以调用方统一走
`AutoFillMapper` 提供的 default 方法，不自己拼参数顺序。

### 两个具体的实现约束

**切点里的 `..` 不能少。**

```java
execution(* com.miuxuer.linkforge.mapper..*.*(..))
```

单个 `*` 只匹配一层包，写成 `mapper.*.*(..)` 的话，一旦 Mapper 被分到子包，
切面会**静默失效** —— 不报错、不警告，只是字段永远填不上。

**填充失败不能让业务失败。** 实体没有对应的 setter（比如某些表没有 `create_user`）、
值为 null、反射调用失败 —— 这些情况一律跳过 + 记日志，而不是抛异常。
公共字段填充是锦上添花的功能，它不该有能力让业务写库失败。

## 七、操作日志切面的三个必须

**1. 必须补异常分支。**

```java
try {
    result = joinPoint.proceed();
    return result;
} catch (Throwable e) {
    error = e;
    throw e;              // 原样抛出去，不能吞
} finally {
    saveLog(...);         // ← 放在 finally，失败的操作也有日志
}
```

如果把写日志的代码放在 `proceed()` 之后，方法一抛异常就不执行了，
结果是**成功的操作有日志、失败的操作反而没有** —— 而失败的操作恰恰最需要追溯。

**2. 必须脱敏。**

登录接口的入参里带着明文密码，原样落库等于把密码抄了一份进日志表 ——
拖库之后攻击者根本不用破解 BCrypt，直接查日志表就行。
切面会在写入前把 `password` / `secret` / `token` / `accessKey` 这类字段替换成 `******`。

**3. 必须截断。**

`error_msg` 是 `VARCHAR(500)`，不预留截断标记的位置会导致 `Data too long` ——
**记日志这个动作反而抛异常**。截断后总长度严格不超过列宽。

## 八、自定义 starter 为什么要拆两个模块

`linkforge-oss-spring-boot-starter`（空壳，只有依赖声明）
+ `linkforge-oss-spring-boot-autoconfigure`（真正的实现）。

- starter 面向**使用者**，autoconfigure 面向**实现**
- 使用者只引 starter 一个坐标，不需要知道里面用了哪个 SDK、有几个配置类
- 以后换掉底层实现（比如改用 MinIO），只动 autoconfigure，引用方一行都不用改

这是 Spring Boot 官方 starter 的统一做法：`spring-boot-starter-data-redis` 是空壳，
真正的自动配置在 `spring-boot-data-redis` 里。

### 两个容易做错的地方

**自动配置类的包名要放在应用的组件扫描范围之外**（本项目是 `com.miuxuer.oss`，
而应用扫描 `com.miuxuer.linkforge`）。

放进扫描范围的话，这个类会被 `@ComponentScan` 扫到，
于是"自动配置到底有没有生效"就验证不出来了 —— 你分不清 Bean 是扫描注册的还是
imports 文件注册的。

**整个 OSS 功能块要包在 `@ConditionalOnProperty` 里。**

```java
@Configuration(proxyBeanMethods = false)
@ConditionalOnProperty(prefix = "aliyun.oss", name = "endpoint")
static class OssClientConfiguration { ... }
```

不这么做的话，引了 starter 但还没配 OSS 的模块会在启动时拿 null 的 endpoint
去初始化客户端然后失败 —— **starter 就不可插拔了**。

## 九、图片上传的三层校验

| 层 | 挡什么 | 为什么不够 |
|---|---|---|
| 大小（Tomcat 层） | 超大文件 | 只挡体积，不挡内容 |
| `Content-Type` | 手滑传错文件 | **客户端说了算**，改个 header 就能骗过去 |
| **文件头魔数** | 改名党 | 读前 12 个字节判断真实格式 |

前两层都是客户端可控的。把 HTML 改名成 `.png` 再声明 `image/png`，
前两层都拦不住。

### 已知边界

魔数只看开头几个字节，**挡不住有意伪造的人**（在文件头塞几个字节即可）。
要真正防住得在服务端把图片解码再重新编码（任何非图片数据都会在这一步丢掉），
开销大得多，本项目没做。

影响有限：文件落在 OSS 的独立域名上，不在应用服务器上，不会被执行；
OSS 按扩展名决定 `Content-Type`，伪装成 `.png` 的文件不会被浏览器当 HTML 渲染。

## 十、自定义 starter 里的 SSRF 防护

二维码的 logo 地址存在 `t_link.qr_logo` 里，**是用户能改的字段**。
服务端拿用户给的地址去发请求，这是教科书式的 SSRF 入口：

- `http://169.254.169.254/latest/meta-data/` 读云厂商实例元数据（可能有临时凭证）
- `http://localhost:3306` 当端口扫描器
- 指向一个永远不返回的地址，把 Tomcat 的线程耗光

三层限制：

1. **只允许 https** —— 挡掉 `file:`、`ftp:` 这类协议
2. **域名必须在 OSS 白名单里** —— 最硬的一层。logo 只能通过 `/api/upload`
   传到自家 bucket，地址必然落在 OSS 域名下
3. **超时 + 大小上限** —— 防慢连接占线程、防大文件读进内存

两个细节：

- **不跟随 302 跳转**。跟随的话，一个白名单域名下的地址可以 302 到内网地址，
  域名校验就白做了
- **用后缀匹配而不是 `contains`**。`oss-cn-beijing.aliyuncs.com.evil.com`
  包含目标字符串但完全受攻击者控制；后缀匹配还要求前面紧跟一个点，
  避免 `eviloss-cn-beijing.aliyuncs.com` 也被放过

失败时**降级成不带 logo 的二维码**，而不是让整个二维码生成失败 ——
OSS 抖一下就返回 500、用户什么都拿不到，比"少个 logo"糟糕得多。

## 十一、看板的数字为什么可能"不一致"

这三个数字来自**两套不同的机制**：

| 指标 | 来源 | 特点 |
|---|---|---|
| 累计访问量 | `t_link.visit_count` + Redis 未同步增量 | **准**（每次访问都 +1），但有最多 5 分钟的同步间隔 |
| 今日访问量 | `t_visit_log` 明细表 | 实时，但明细在队列打满时会丢行 |
| 访问趋势 | `t_visit_log` 明细表 | 同上 |

所以"累计访问量"和"今日访问量之和"可能对不上。**这不是 bug，是两套机制各自的取舍**：
总量要准，明细要能按天/按来源拆开看。

### 为什么要把 Redis 增量加上

只读 `t_link.visit_count` 的话，用户访问完自己的短链立刻打开看板会看到 0 ——
数据没错（还没到同步周期），但在用户眼里就是"这功能坏了"。
Redis 里那些 `linkforge:link:visits:*` 存的正是"自上次同步以来的增量"
（定时任务取走之后会删掉 key），两边相加就是精确值，而且没有滞后。

### Top N 的排序必须在补完增量之后做

数据库里的 `visit_count` 是每 5 分钟同步一次的值，而排序必须建立在
"加上 Redis 增量之后"的数值上。在 SQL 里按旧值排好序、之后每条再补增量的话，
**补完列表就乱了** —— 用户会看到"第 1 条 3 次、第 3 条 10 次"这种明显没排序的排行。

增量只存在于 Redis，SQL 里拿不到，所以只能先把候选集取出来、补完增量再排序。
代价是要加载该用户的全部短链 —— 但"一个用户有多少条短链"天然是有限的。

### 趋势图要补零

SQL 的 `GROUP BY` 只会返回"有访问记录"的日期。缺的那几天直接丢给前端画折线图的话，
**x 轴会缺刻度** —— 图看起来是连续的、其实把 3 天的数据挤在了一起，
属于最难发现的那类错误。后端在返回前会把整个日期区间补齐。

## 十二、已知限制与后续可做的事

按优先级排列：

1. **访问明细的异步队列会丢数据**。极端情况下（队列打满、服务崩溃）会丢明细。
   上 RabbitMQ 或 Kafka（持久化 + ACK）可以解决
2. **限流是单机维度的**。目前基于 IP + Redis，多实例部署时额度是共享的（这点没问题），
   但 `VisitCountSyncTask` 的定时任务在多实例下会重复执行 ——
   需要加分布式锁或改成单实例调度
3. **缓存清理没有处理 Redis 不可用的情况**。停用短链时如果 Redis 挂了，
   缓存里的旧值要等自然过期才失效
4. **短链支持自定义过期时间，但删除的短链不会从布隆过滤器里移除**。
   影响很小（只是多一次穿透到 DB 的查询），但如果删除量很大，
   需要一个可删除的布隆过滤器（比如布谷鸟过滤器）或定期重建
5. **没有"找回密码"**。需要邮件服务，超出了本项目范围
6. **前端没有做移动端适配**。目前的布局是按桌面端设计的
